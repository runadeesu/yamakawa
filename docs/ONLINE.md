# オンライン機能 (アカウント / フレンド / チャット / 対戦)

やまかわてるきゲームのオンライン版。**表示名 + パスワードだけ**で登録でき、メールアドレス・電話番号・メール認証は一切ありません。
ひとりで遊ぶモードは従来どおりそのまま動き、オンライン設定が無い(または通信できない)場合もゲーム本体は落ちません。

- 構成: **Supabase** (Auth + PostgreSQL + Realtime + Edge Function) / クライアントは React (既存)
- サーバーの秘密鍵 (`service_role` / `sb_secret_…`) はブラウザに一切入りません。ブラウザが持つのは公開用の URL と publishable key だけです。

---

## 1. 仕組み

```
ブラウザ (React)                          Supabase (専用プロジェクト)
┌──────────────────────┐   HTTPS   ┌──────────────────────────────────────────┐
│ OnlineProvider       │──────────▶│ Edge Function `account`  (signup / login) │
│  ログイン状態・通知   │           │   入力検証 / レート制限 / 内部メール割当   │
│ api.ts (RPC)         │──────────▶│ PostgREST → public.* の RPC (SECURITY     │
│ VersusRunner         │           │   DEFINER, 全て auth.uid() を検証)         │
│  対戦の進行・提出     │◀─WebSocket─│ Realtime: postgres_changes (RLS 付き)     │
│                      │           │           private Broadcast `match:<id>`  │
└──────────────────────┘           │ PostgreSQL: RLS / 制約 / pg_cron          │
                                   └──────────────────────────────────────────┘
```

### アカウント (表示名 + パスワード)

Supabase Auth はメールを識別子にするため、**ユーザーに見せない内部メール** `p<32桁の乱数>@players.teruki.example` を割り当てます。

1. ブラウザは Edge Function `account` に `{action, name, password}` を送る (`verify_jwt = false`。ログイン前に呼ぶため)
2. 関数が表示名を検証・正規化 (NFKC、2〜16文字、英数字・`_`・`-`・かな・カナ・漢字、予約語禁止、ASCII 大文字小文字は同一視) し、パスワードを検証 (8文字以上・72バイト以下・弱いパスワード禁止)
3. **レート制限**: ログイン失敗は表示名ごと 5 回 / 15 分・IP ごと 20 回 / 15 分、サインアップは IP ごと 6 回 / 時間。IP はサービスキーを胡椒にしてハッシュ化して保存 (生の IP は保存しない)
4. admin API で Auth ユーザーを作成 (`email_confirm: true`, `app_metadata.teruki = '1'`) → `players` 行を作成 → セッションを返す
5. ブラウザは受け取った `access_token` / `refresh_token` を `supabase-js` に渡す。以後は通常の Supabase セッション (自動更新、`localStorage` に保存して再起動後も復元)

- パスワードは Supabase Auth が **bcrypt でハッシュ化**して保存します (平文は保存されません)。
- 存在しない表示名・形式が不正な入力・パスワード違いは**すべて同じ応答** (`bad_credentials`) で、アカウントの有無を漏らしません。
- 公開サインアップ経由で作られたユーザーは、`auth.users` の**コミット時に走る遅延制約トリガー** (`teruki_guard_auth_users_commit`) が `app_metadata.teruki = '1'` を確認して拒否します (admin 作成は「INSERT → 同一トランザクションで app_metadata を UPDATE」の順なので、INSERT 時点ではなくコミット時に検査)。匿名サインインは無効です。
- ログアウトは「この端末」と「すべての端末 (global)」を選べ、端末のセッションは必ず消去されます。

> ⚠ **パスワードリセットはありません (初期バージョンの仕様)。** メールアドレスを持たないため、安全に本人確認する手段がありません。
> パスワードを忘れるとそのアカウントには入れません。ログイン画面・登録画面・設定画面にその旨を表示しています。
> (将来の案: 再発行コードの発行、端末に紐づく復旧キー など)

### データ設計 (`supabase/migrations/`)

| テーブル | 役割 |
|---|---|
| `players` | 表示名・`name_key` (一意)・プレイヤーID (8文字)・戦績 (`matches = wins + losses + draws` を CHECK で保証) |
| `friendships` / `friend_requests` | フレンド関係・申請 (同じ2人の未処理申請は 1 件だけ: 部分一意インデックス) |
| `player_blocks` | ブロック / ミュート |
| `conversations` / `messages` / `conversation_reads` | 友達チャット・対戦チャット・未読位置 |
| `reports` | 通報 (理由・対象メッセージ・対戦 ID) |
| `matches` / `match_players` / `match_invites` | 対戦・参加者ごとの結果・フレンド招待 |
| `app_private.*` | 外部公開しない内部テーブル: レート制限、ログイン用の内部メール、対戦の出現順 (`match_seeds`)、マッチ待ち行列、不正ログの記録、NG ワード |

- `public` のテーブルは **すべて RLS 有効**。クライアントに許す権限は「自分が関係する行の SELECT」だけで、**INSERT / UPDATE / DELETE の権限は付与していません**。書き込みは SECURITY DEFINER の RPC (`set search_path = ''`、冒頭で `auth.uid()` と `players` の存在を検証) だけが行います。
- `app_private` スキーマは PostgREST に公開されず、`anon` / `authenticated` からは見えません。
- `svc_*` 関数 (ログイン照会・プレイヤー作成・レート制限) は `service_role` 専用で、一般ユーザーは実行できません。
- エラーは `errcode P0001` + メッセージ = エラーコード (`rate_limited`, `not_found`, `forbidden`, …) で返し、クライアントが日本語メッセージに変換します。

### フレンド / ブロック / 通報

- 検索は表示名の**前方一致**かプレイヤーID (自分自身・自分をブロックした相手は出ない。`%` `_` はエスケープして全件列挙を防止。2〜16文字、1 分 40 回まで)。
- 申請: 重複・自分自身・すでにフレンド・ブロック中は拒否。互いに申請し合ったら自動で成立。連投制限 (1 時間 20 件、同じ相手へは 1 日 3 回)。
- 一覧のオンライン状態は 25 秒ごとの生存報告 (`heartbeat`) から判定 (75 秒途絶えるとオフライン)。`オンライン / マッチ待機中 / 対戦中 / オフライン`。
- **ブロック**: フレンドから外し、相手からの申請・メッセージ・招待・マッチングを遮断。**ミュート**: フレンドのまま、相手のメッセージだけを履歴にも Realtime にも出さない (相手には通知されない)。
- 通報はサーバーの `reports` に記録されます (運営がデータベースで確認する運用。管理画面は未実装)。

### チャット

- 友達 1:1 と対戦中の 2 人チャット。送信は RPC のみ。受信は Realtime (`messages` の INSERT、**RLS でフィルタ**) と、使えない環境向けの定期更新 (4〜20 秒) の両方。
- サーバー側の検証: Unicode 正規化、不可視文字・方向制御文字・制御文字の除去、`<` `>` の全角化、NG ワードの伏せ字化 (`app_private.ng_words` を運用で追加・削除)、1〜200 文字、**30 秒に 20 件**、0.5 秒未満の連投禁止、同じ本文の 10 秒以内の再送禁止。
- 画面側: 本文は**常にテキストとして描画** (`dangerouslySetInnerHTML` は不使用)。入力欄は IME 変換中の Enter で送信されず、送信中は二重送信できません。
- 未読数: 会話ごとの既読位置をサーバーで管理し、タブのバッジ・一覧に表示。
- **保存と削除のルール**: 友達チャットは**直近 30 日・1 会話あたり最新 500 件**まで。対戦チャットは**試合の 7 日後に削除**。`pg_cron` が毎日 03:17 (UTC) に整理します (`app_private.purge_old_data`)。`pg_cron` が無い環境でも、`heartbeat` がときどき同じ整理を実行します。
- ミュート / ブロックした相手のメッセージは、履歴にも Realtime にも出ません (RLS: `hides_sender`)。ブロックするとフレンドも解除されるので、相手は送信自体できなくなります。

### オンライン対戦

既存ルールのままの**リアルタイム 2 分間スコアバトル**です。両者に**同じ順番 (サーバーが決めた 400 個の出現順)** でてるきが落ちてきて、2 分後に高得点の勝ち。先にゲームオーバーになった人がいて、残った人がそのスコアを上回った時点でも決着します。

1. **マッチ成立**: クイックマッチ (待機 2 分で時間切れ) またはフレンド招待 (有効期限 60 秒、相手がオフラインなら案内して送らない)
2. **同期**: 両者が `ready` を送るとサーバーが `starts_at = 今 + 4 秒` / `ends_at = + 120 秒` を決定。クライアントはサーバー時刻との差 (RTT 最小の応答から推定) で補正し、カウントダウン → 開始。準備は 25 秒以内
3. **プレイ**: 各自のブラウザで物理を回します (既存の `GameSession` をそのまま使用)。出来事を `[step, kind, arg]` の短いログに記録 (`drop` / `merge` / `gameover`)。`step` は**対戦開始からの 60Hz の物理ステップ数**
4. **提出と判定**: 終了時にログを `match_finish` で提出。**サーバーがログを検証して得点を自分で再計算**し、勝敗を決めて戦績を更新します (1 回だけ・冪等)
   - 出現順どおりか、存在しない合体・落下間隔 (27 ステップ未満)・フィールド面積を超える数・4000 イベント超・時刻の逆行/超過 (`step ÷ 60` が実経過時間 +1.5 秒を超える = 速度改ざん) を拒否
   - 拒否されたログは `app_private.match_violations` に記録 (`invalid_log` を返す。例外にはしない)
   - 二重送信・遅れて届いた送信は結果を変えません
5. **通信状態**: 盤面スナップショット (250ms ごと、Realtime Broadcast、表示専用) が届けば「良好」。届かない環境では**サーバーが数える「相手の最後の生存報告からの経過」** (`idle_ms`) で判定 (8 秒未満 良好 / 16 秒未満 不安定 / それ以上 途切れ)
6. **切断**: 生存報告 (3 秒ごと) が **25 秒**途絶えたプレイヤーは棄権扱い (相手の勝ち)。終了後 20 秒以内に結果が届かなくても棄権扱い。両者棄権は無効試合 (戦績に入らない)。`pg_cron` が毎分、放置された試合を整理
7. **一時的な切断**: 結果の提出は指数バックオフで最大 8 回再試行。25 秒以内に回復すれば対戦は続きます

#### 限界 (正直に)

- 物理演算そのものはサーバーで再実行しません。サーバーが検証するのは**ログの整合性** (出現順・得点規則・時間・面積・落下間隔) で、「正しい物理の結果か」までは確認できません。物理を完全に再現する権威サーバーが必要になったら、同じ `GameSession` を Node 上で回す構成に拡張できます。
- 対戦中にページを再読み込みすると、その対戦は**棄権扱い**になります (盤面の復元は未実装)。ロビー待機中の再読み込みは復帰できます。

### Realtime が使えない環境

WebSocket が通らないネットワーク (社内プロキシ・学校など) では、画面に「リアルタイム通信が使えないため、数秒ごとの自動更新で動いています」と表示し、**定期更新 (4〜6 秒) だけで全機能が動きます** (フレンド申請・招待・チャット・対戦の進行)。盤面スナップショット (相手の小さな盤面表示) だけは出ません。

## 2. セットアップ

### 必要なもの

- Node.js 22 (動作確認済み)
- Supabase プロジェクト (無料枠で可)。**メール認証は使わない**ので、SMTP の設定は不要です

### 環境変数 (クライアント)

`.env.example` を `.env.local` にコピーして値を入れます。**どちらも公開してよい値**です。

| 変数 | 内容 |
|---|---|
| `VITE_SUPABASE_URL` | `https://<project-ref>.supabase.co` |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | `sb_publishable_…` (ダッシュボード → Project Settings → API Keys) |

- 本番ビルド用の値は `.env.production` にコミット済みです (公開値のみ)。別プロジェクトを使うときは書き換えてください。
- どちらかが空だとオンライン機能は無効になり、タイトル画面に「オンライン対戦はこのビルドでは無効です」と出ます。ゲーム本体は動きます。
- **`service_role` / `sb_secret_…` は絶対にフロントエンドの環境変数 (`VITE_*`) に入れないでください。** Edge Function の環境変数は Supabase が自動で注入します。

### データベースの作り方

`supabase/migrations/` を**ファイル名の順**に適用します。

```bash
# Supabase CLI を使う場合
supabase link --project-ref <project-ref>
supabase db push
```

| ファイル | 内容 |
|---|---|
| `…0100_core.sql` | players・レート制限・Auth ガード・サービス専用関数 |
| `…0200_social.sql` | フレンド・ブロック・通報・検索 |
| `…0300_match_core.sql` | 対戦・ログ検証・結果確定・棄権処理 |
| `…0310_matchmaking_invites.sql` | クイックマッチ・招待 |
| `…0320_chat_profile.sql` | チャット・プロフィール・保存期間の整理 |
| `…0400_realtime_grants.sql` | Realtime の公開テーブル・pg_cron・権限の整理 |
| `…0500_broadcast_policies.sql` | 対戦チャンネル (private Broadcast) のアクセス制御 |
| `…0600_match_liveness.sql` | 相手の接続状態 (`idle_ms`) |

**注意 (順序)**: `…0500` は `realtime.messages` テーブルが必要です。新規プロジェクトでは**一度 Realtime に WebSocket 接続してから** (アプリを 1 度開く、または `e2e/realtime.mjs` を 1 度実行する) 適用してください。テーブルが無いと `relation "realtime.messages" does not exist` で失敗します。

**注意 (Supabase MCP / SQL エディタ)**: 長い `DELETE` を含む関数をまとめて流すと途中で止まることがあるため、整理用の関数は「1 関数 1 DELETE」に分けてあります。

### Edge Function `account` のデプロイ

```bash
supabase functions deploy account --no-verify-jwt --project-ref <project-ref>
```

- `--no-verify-jwt` が必須です (ログイン前に呼ぶ関数のため)。認可は関数内の検証とレート制限が担います。
- 環境変数 `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` / `SUPABASE_ANON_KEY` は Supabase が自動で渡します。

### Supabase ダッシュボードで確認・設定すること

1. **Authentication → Sign In / Providers → "Allow new users to sign up" を OFF** にする (推奨)。サインアップは Edge Function (admin API) だけが行うので、公開サインアップ API を閉じても動きます。DB の制約トリガーでも防いでいますが、入口でも閉じるのが安全です。※ この設定は私の作業用ツールからは変更できなかったため、**手動で行ってください**。
2. Anonymous sign-ins は OFF (現状 OFF を確認済み)。
3. Authentication → Sessions: JWT の有効期限 (既定 1 時間) とリフレッシュトークンのローテーションは既定のままで可。
4. Database → Extensions: `pg_cron` を有効化 (migration 0400 が可能なら自動で有効化し、毎分・毎日のジョブを登録します)。

## 3. テスト

```bash
npm test                    # 単体 + DB 結合 (PGlite) 95 件
npm run build && npm run e2e            # 一人用ゲームの実ブラウザ E2E (89 項目)
npm run build && npm run e2e:online     # オンライン: 実ブラウザ 2 台 × 実 Supabase (82 項目)
NODE_USE_ENV_PROXY=1 npm run e2e:realtime   # Realtime: 3 クライアント × 実 Supabase (26 項目) ※プロキシ越しの環境のみ NODE_USE_ENV_PROXY=1
```

- `e2e:online` / `e2e:realtime` は**本物のバックエンド**にテスト用アカウント (`zz_e2e_*`) を作ります。作成にはサインアップの IP 制限 (1 時間 6 回) がかかるので、続けて実行するときは間隔をあけるか、`app_private.rate_limits` の `signup:*` / `login:*` 行を消してください。
- DB の単体テストは PGlite (WASM の PostgreSQL) 上で本物の migration を流し、`bootstrap.sql` で Supabase のロール・`auth.uid()`・Realtime を再現します。`golden.test.ts` は**実際の `GameSession`** で遊んだログをサーバーの SQL に通し、クライアントとサーバーのルール (得点・コンボ・合体) が一致することを確認します。

### 検証できていないこと / 制約

- **別の端末・別のネットワーク**: 実際に物理的に別の端末で試してはいません。上のテストは、同一マシン上の独立したブラウザセッション (別プロファイル扱い) と独立した Node クライアントが、インターネット経由で Supabase につないだものです。サーバーは公開インターネット上にあるので別ネットワークでも動く設計ですが、実機での確認はあなたの環境で行ってください。
- **ブラウザでの Realtime (WebSocket)**: 私の検証環境 (企業向けのプロキシ) では Chromium の WebSocket が通らなかったため、ブラウザ E2E は「リアルタイム通信が使えない」自動更新モードで検証しています。WebSocket そのものは Node の supabase-js で実サーバーに対して検証済みです (上の表 #8)。通常のネットワークのブラウザでの WebSocket 動作は、同じ `supabase-js` なので問題ない見込みですが、**ここでは未検証**です。
- **公開サインアップ API の遮断**: 実サーバーでは、匿名サインイン拒否と、予約ドメインのメールアドレス拒否を確認しました。DB の制約トリガーが実際のメールでの公開サインアップを拒否する動作は、PGlite の DB テストでは確認済みですが、実サーバーでは (第三者のアドレスにメールを送る恐れがあるため) 試していません。上の「ダッシュボードで確認・設定すること」の 1 を行ってください。
- 物理演算のサーバー側再計算はありません (上の「限界」参照)。

## 4. セキュリティの要点

| 項目 | 対策 |
|---|---|
| パスワード | Supabase Auth が bcrypt でハッシュ化。72 バイト上限・弱いパスワード拒否 |
| ログイン総当たり | 表示名ごと・IP ごとの失敗回数制限 (関数側)。存在しない名前でも同じ応答と同程度の応答時間 |
| セッション | JWT (1 時間) + 自動更新のリフレッシュトークン。ログアウトで端末の保存を消去、全端末ログアウトに対応 |
| 認可 | 全テーブル RLS・書き込み権限なし。書き込みは RPC のみで、全 RPC が `auth.uid()` を検証 |
| 秘密鍵 | クライアントに無し。Edge Function だけが service role を使う |
| SQL インジェクション | パラメータ化された RPC のみ。検索のワイルドカードはエスケープ。動的 SQL なし |
| XSS | メッセージ・表示名は常にテキスト描画。サーバー側でも `<` `>` 等を無害化 |
| スパム | チャット (30 秒 20 件・0.5 秒間隔・重複禁止)、申請・招待・検索・通報・ブロック・マッチ参加すべてに回数制限 |
| 対戦の不正 | ログ検証 (出現順・得点・時間・面積・間隔)・結果の冪等確定・違反の記録・戦績は RPC だけが更新 |
| 通信の暗号化 | すべて HTTPS / WSS (TLS) |
| 個人情報 | 表示名・パスワード (ハッシュ)・戦績・チャットだけ。IP は生で保存せずハッシュのみ (レート制限用・2 日で削除) |
| 通報・ブロック | 実装済み (通報の確認画面は未実装。データベースで確認) |

## 5. テストデータの掃除

E2E は `zz_e2e_*` (と手動スモークの `zz_smoke*`) という表示名のアカウントを作ります。不要になったら、Supabase の SQL エディタで次を実行します (`auth.users` の削除は `players` 以下へカスケードします)。

```sql
delete from auth.users where id in (
  select id from public.players where name like 'zz\_e2e\_%' or name like 'zz\_smoke%'
);
```
